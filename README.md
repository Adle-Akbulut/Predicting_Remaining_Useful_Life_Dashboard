## 1. Problem Statement

Unplanned machine failure is one of the most expensive problems in manufacturing and heavy industry: it causes unplanned downtime, emergency repair costs, scrapped batches, and safety risk.

Most maintenance programs are either:

- **Reactive** — fix it after it breaks (expensive), or
- **Preventive** — fix it on a fixed schedule (wastes useful component life).

**Predictive maintenance** asks a better question:

> *"Given this machine's sensor history, how many operating cycles does it have left before failure — and which machines should we service first?"*

This project answers that question end-to-end: raw sensor data → feature engineering → ML model → evaluation → saved artifacts → an interactive dashboard a maintenance planner can actually use.

---

## 2. What This Project Does

- **Ingests** raw run-to-failure sensor telemetry (NASA C-MAPSS turbofan dataset: 21 sensors + 3 operating settings per cycle).
- **Engineers features** per engine: time features plus rolling mean / rolling standard deviation windows over every sensor channel (trend + volatility signals, computed using only past data — no leakage).
- **Trains** a gradient-boosted regressor (XGBoost) inside a scikit-learn `Pipeline` (imputation → scaling → model).
- **Evaluates** with maintenance-relevant metrics: MAE, RMSE, R², and *% of predictions within ±10 / ±20 cycles*.
- **Persists artifacts** (`model.joblib`, `feature_columns.json`, `metadata.json`) so training and serving stay consistent.
- **Serves** predictions through a Streamlit dashboard with:
  - fleet-level health overview and risk ranking,
  - per-engine drill-down with sensor trends and predicted-RUL curves,
  - **configurable critical / warning thresholds** (a business knob, not a hardcoded constant),
  - raw CSV upload with a downloadable template,
  - model performance and feature-importance transparency.

## 4. Dataset

[NASA C-MAPSS Turbofan Engine Degradation Simulation Dataset](https://www.kaggle.com/datasets/bishals098/nasa-turbofan-engine-degradation-simulation) (simulated run-to-failure trajectories).

| File | Contents |
|---|---|
| `train_FD00X.txt` | Full run-to-failure trajectories (26 columns: unit, cycle, 3 settings, 21 sensors) |
| `test_FD00X.txt` | Truncated trajectories (machines still alive at last observed cycle) |
| `RUL_FD00X.txt` | True remaining cycles at the last observed cycle of each test unit |

- **Target:** Remaining Useful Life (RUL) = cycles remaining before failure.
- **RUL cap:** targets are capped at **125 cycles** (standard practice for C-MAPSS): early-life cycles carry little degradation signal, and capping focuses the model on the operationally relevant near-failure region.
- Subsets `FD001` (1 operating condition, 1 fault mode) and `FD002` (6 operating conditions, 1 fault mode) are supported by changing the file names in `train.py`.

```text
│   ├── model.joblib
│   ├── feature_columns.json
│   └── metadata.json
├── src/
│   ├── data/
│   │   └── preprocess.py      # loading, RUL target creation, engine-group split
│   ├── features/
│   │   └── build_features.py  # rolling-window feature engineering
│   ├── models/
│   │   ├── train.py           # pipeline definition, training, artifact saving
│   │   ├── evaluate.py        # regression metrics (MAE/RMSE/R²/within-N)
│   │   └── predict.py         # artifact loading + inference on raw data
│   └── utils/
│       └── io.py              # JSON / directory helpers
├── requirements.txt
└── train.py                   # orchestration: data → features → model → artifacts
```

**Design principle:** each layer owns exactly one responsibility. The dashboard never trains or transforms data itself — it reuses the *same* feature code and saved artifacts produced by training, so training and serving cannot drift apart.

## 8. How It Works

### 8.1 Preprocessing (`src/data/preprocess.py`)

- Parses the whitespace-delimited C-MAPSS files and names all 26 columns.
- Builds the RUL target: `rul = max_cycle_of_engine − current_cycle` (train), and `rul = rul_at_end + (max_cycle − current_cycle)` (test).
- **Engine-grouped split:** validation engines are disjoint from training engines. Splitting random *rows* would leak an engine's own history into both sets and inflate scores.
- Caps RUL at 125.

### 8.2 Feature engineering (`src/features/build_features.py`)

| Group | Features | Why |
|---|---|---|
| Time | `cycle`, `cycle_log`, `cycle_squared` | Age of the machine is the strongest degradation driver |
| Raw signals | 3 settings + 21 sensors | Current operating state |
| Rolling mean (windows 5, 10) | 42 features | Short/medium-term trend of each sensor |
| Rolling std (windows 5, 10) | 42 features | Growing instability is a classic pre-failure signature |

All rolling windows use **only current and past cycles** (`min_periods=1`), so no future information ever leaks into a prediction.

### 8.3 Model (`src/models/train.py`)

```text
Pipeline: SimpleImputer(median) → StandardScaler → XGBRegressor
```

| Hyperparameter | Value |
|---|---|
| `n_estimators` | 350 |
| `learning_rate` | 0.05 |
| `max_depth` | 4 |
| `subsample` / `colsample_bytree` | 0.9 / 0.9 |

XGBoost was chosen because gradient-boosted trees are the strongest classical baseline for tabular sensor data: fast, robust to mixed scales, and interpretable via feature importances.

### 8.4 Evaluation protocol (`src/models/evaluate.py`)

- **Last-cycle evaluation:** metrics are computed on the *latest available reading* per engine — the exact decision point a maintenance planner faces. Evaluating every historical row would over-weight easy, healthy early cycles.
- **Metrics:** MAE, RMSE, R², and the business-friendly *within ±10 / ±20 cycles* hit rate.

### 8.5 Serving (`src/models/predict.py` + `app/main.py`)

The dashboard loads the saved pipeline and feature list, rebuilds features with the *same* code used in training, and predicts. Uploaded raw CSVs go through the identical path, so local files and live uploads behave exactly the same.

## 9. Example Results

Run on **FD002** (259 test engines), RUL capped at 125:

| Split | MAE | RMSE | R² | Within ±10 cycles |
|---|---|---|---|---|
| Validation (last cycle of held-out engines) | **5.56** | **6.87** | – * | **82.7 %** |
| Test (last cycle of test fleet) | **12.94** | **16.83** | **0.85** | **49.4 %** |

\* R² is undefined on the validation split because run-to-failure training engines all have true RUL = 0 at their final cycle (a constant target); MAE and the ±10-cycle hit rate are the meaningful measures there — an average end-of-life prediction error of ~5.6 cycles.

Fleet-level view (FD002 test fleet): **259 engines, average predicted RUL 74.25 cycles**. With thresholds set to 19 (critical) / 86 (warning), the fleet classifies into **40 critical / 88 warning / 131 healthy** engines — moving the sliders re-triages the fleet instantly, which is exactly how a planner would explore maintenance policies.

Top drivers learned by the model: `cycle` (age), followed by sensor channels **11, 15, 4, 13, 12** and their rolling statistics — consistent with the known informative channels in C-MAPSS.

> Numbers vary by subset (`FD001` vs `FD002`), split seed, and hyperparameters. Re-run `python train.py` to reproduce on your machine.

## 10. Dashboard Guide

| Tab | Purpose |
|---|---|
| **Fleet** | KPIs (engines, avg predicted RUL, critical/warning counts), status distribution bar chart, top-25 highest-risk engines table |
| **Engine detail** | Pick any engine: latest predicted vs true RUL, multi-select sensor trend charts, predicted-RUL-over-time curve |
| **Model performance** | Validation & test metrics, top-15 feature importances |
| **Data preview** | Raw + predicted rows for sanity checks |

**Sidebar controls**

- **Critical / Warning thresholds (cycles remaining):** sliders that re-classify every engine live (`RUL ≤ critical → Critical`, `RUL ≤ warning → Warning`, else `Healthy`). The warning slider's minimum is locked above the critical slider, so invalid policies are impossible.
- **Data source:** switch between the bundled sample fleet and **Upload raw CSV** (with a one-click CSV template download defining the expected 26-column schema).

## 11. Troubleshooting

| Symptom | Fix |
|---|---|
| `FileNotFoundError: data/raw/train_FD001.txt` | Dataset not placed correctly. Files must sit directly in `data/raw/` (not in a zip subfolder). Verify with `Test-Path .\data\raw\train_FD001.txt` (PowerShell). |
| `ModuleNotFoundError: No module named 'src'` | Run commands from the project root: `python train.py`, `streamlit run app/main.py`. |
| Dashboard shows an old model after retraining | Streamlit caches artifacts — restart the app or clear the cache. |
| `train_FD001.txt.txt` | Windows hid the extension when saving; rename the file. |
